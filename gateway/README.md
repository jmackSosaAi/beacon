# Beacon gateway and daily assistant

Deployed at https://your-worker.example.workers.dev. React interface, Cloudflare Worker, D1 storage, five-minute scheduler and Web Push. See [accountability behavior](../ACCOUNTABILITY.md).

## Open it

From this directory, run `node scripts/beacon.mjs access-link`, then open the printed local HTML path. Each private link signs in one device, expires in 15 minutes, and cannot be reused. Minting a link needs the laptop-only admin key (`~/.config/jarvis/admin_key`), sends a security push, and is audited. Delete the HTML file after opening it. The resulting `__Host-jarvis_session` cookie (Secure, Path=/, no Domain) lasts 30 days, or ends after 7 days without use. The old `jarvis_session` name is still read but never set; drop it after existing sessions lapse (30 days after deploy). Each sign-in stores a device label picked in code from a fixed list (e.g. "Safari on iPhone", never the raw User-Agent) and sends a "New Beacon sign-in" security notice with the Telegram **Not me → pause Beacon** button. Connections → **Sign out all devices** (`POST /api/logout-all`) deletes every session. Generate another link for a second device. Never commit or share access tokens.

On iPhone, add Beacon to the Home Screen, open it there, then enable notifications under Connections. Use **Send a test** to verify delivery. Without device permission, prompts remain in the app inbox; existing Calendar popups work independently. A service-worker registration alone does not prove delivery.

## Live vs pending

- Capture, all-tasks list, work check-ins, reported Persian minutes, prompts and source-health display are deployed.
- Calendar is initially a snapshot through October 16. Snapshot prompts continue through its coverage; later Calendar edits require reimport or OAuth. Expired snapshots stop work-block prompts.
- Calendar/Gmail polling every 15 minutes requires Google OAuth below. School forwarding is not verified. Canvas is blocked and Discord is not connected.
- Chat uses Workers AI unless `ANTHROPIC_API_KEY` is configured. The UI identifies the configured provider. Conversation failure leaves capture/check-in forms available. No external-send or calendar-write tools are exposed to the model.
- Voice fails closed: it requires `VOICE_ENABLED=true` **and** a keypad PIN (`node scripts/beacon.mjs voice-pin`). The PIN is entered on the keypad, 3 tries per call and 5 failures a day trigger a lockout. Only the word "confirm" approves, within 60 seconds of a read-back generated by code. Existing GroupMe read routes are retained.
- Automatic missed-work rescheduling is off and has no implementation path.
- GroupMe (`src/groupme.js`, needs the `GROUPME_TOKEN` secret; without it source health shows `groupme: not connected`): every 15 minutes the scheduler checks "Club Announcements" only. The group id and checkpoint live in `settings` (`groupme_group`, `groupme_since`); the first run baselines without alerting, and messages older than 6 hours never alert. Code rules decide first (time + event + place, or a change/cancellation → notify; no date/time, system or injection-like text → ignore); the rest go to Claude with no tools (~300 scrubbed characters, enum + reason, purpose `groupme` in `llm_usage`, max 10 per run; no model → ignore, counted as unsorted). Alerts read "📣 Club: <first 200 characters>" built by code with links, addresses and numbers removed; health/account wording sends a generic "details withheld" line. Paused → no check. No migration.

## Telegram

Bot @jmackSosaAi_bot posts to `POST /telegram/webhook` (registered with `secret_token` and `allowed_updates: message, callback_query`). Worker secrets: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OWNER_ID`, `TELEGRAM_WEBHOOK_SECRET`. Only the owner's private chat is accepted. Commands (`/stop`, `/status`, `/help`) are handled in code before any model call. `/stop` sets the D1 `paused` flag that every executor checks, and only the web app can resume. Proposed actions arrive as Approve/Cancel cards generated by code. Notifications are mirrored to Telegram as plain text, so keep sensitive content out of notification bodies. Email alerts carry 👍 Matters / 👎 Ignore buttons; votes are stored on the `mail_items` row. A domain with 3+ Ignore and no Matters is demoted to the digest by code (`sender_rules`; never applies to phishing or school records). `/rules` lists rules and `/rules remove <domain>` deletes one. On Sunday, during the weekly window, Beacon sends a "Proposed CRITERIA.md changes" message built from the votes; it never edits CRITERIA.md. `/status` also shows today's Claude calls, tokens and estimated cost. `/contacts` lists saved contact names (numbers and addresses stay in D1).

## Contacts, drafts and call bridging (M3, migration 0011)

- **Contacts** (`contacts` table; `src/contacts.js`): "add a contact: Sam Lee, 773-555-0142, sam@…" becomes a Confirm-tier Approve card that reads back the full number and email. The number and email must appear in Jackson's own message (US numbers only, stored E.164). Only `web`, `telegram` and `voice` origins can propose one; voice can propose but the card goes to Telegram. Add-only: no edit or delete yet (needs step-up).
- **Drafts** (Draft tier): "draft an email to Sam saying …" sends Telegram a plain-text message starting `✉️ Draft — copy and send it yourself`, with `To:` built from the contacts row (never model text) and links Jackson didn't type stripped from the body. Max 10 a day, blocked while paused, audited as `draft:sent-to-jackson`. There is no Gmail send/compose code; `npm test` greps `src/` to keep it that way.
- **Call bridging** (Confirm tier): "call Sam" proposes `Call Sam Lee at (•••) •••-0142`. On approval (Telegram or web, never voice) Twilio rings `OWNER_NUMBER`; the one-use `POST /voice/bridge?t=` TwiML (Twilio-signed, voicemail hangs up) says "Connecting you to Sam Lee" and `<Dial timeLimit="3600" callerId=TWILIO_NUMBER record="do-not-record">` the number from the table. Max 5 an hour (`bridge_calls`), paused checked at approval and when Twilio fetches the TwiML. A proposal is void if the contact's number changed after the read-back. Needs `TWILIO_SID`, `TWILIO_TOKEN`, `OWNER_NUMBER`, `TWILIO_NUMBER`; without them approval fails with "not set up".
- **Actions view**: web app → Actions tab, `GET /api/actions` (user session) returns the newest 50 audit rows `{action,target_id,created_at}`.

## Finance alerts (M4, migration 0012)

- **Charges** (`src/finance.js`): in Gmail triage, mail from Bank of America (`bankofamerica.com`, `ealerts.bankofamerica.com`, `bofa.com`) or American Express (`americanexpress.com`, `welcome.americanexpress.com`, `aexp.com`) that passes DKIM/DMARC and reads like a charge (not a statement, payment, refund or balance notice) is parsed by regex from subject + snippet into merchant, amount and date. Phishing- or injection-flagged mail is never parsed. These emails never reach the model; `mail_items` keeps only `[card alert — charge recorded]` at level `ignore`. Any run of 4+ digits is stripped from merchants, so no card or account numbers are stored (`charges` table: issuer, merchant, amount, date only).
- **Alerts**: `💳 $X at MERCHANT` (plain text, kind `finance`) only for a new merchant (first two words not seen before and no known subscription matches), an amount over `preferences.chargeAlertMin` (default 100; `POST /api/preferences {"chargeAlertMin":N}`), or a known subscription billed >5% off its imported amount ("Price change: …"). Everything else is just stored. Paused → stored, no alert.
- **Subscriptions** (`known_subscriptions`): `POST /api/import/subscriptions` (admin key only) takes `{subscriptions:[{name,amount,cadence?:"monthly"|"annual",billing_day?,next_due?:"YYYY-MM-DD",pattern?}],replace?}`, max 100. `pattern` (default: the normalized name) matches charge merchants. `replace:true` deletes rows missing from the list, only for the cadences in the list. `node scripts/import-subscriptions.mjs [--dry-run]` reads the Active table of `../finance/subscriptions.md` locally and posts name, monthly amount and billing day with `~/.config/jarvis/admin_key`. Annual entries (with `next_due`) are posted by hand to the same route; a matching charge moves `next_due` a year ahead.
- **Reminders** (scheduler, outside quiet hours, not while paused): `🔁 NAME renews in N days` once, 1-3 days before an annual `next_due` (past dates roll forward a year), and `🔁 Subscriptions this month` on the 1st with the count and monthly total (annual ÷ 12).

## Career engine (M5, migration 0013)

- **Outreach nudges** (`src/outreach.js`, `outreach` table): `POST /api/import/outreach` (admin key only) takes `[{id,name,org,sent_at,last_reply_at,status,domain?}]` or `{outreach:[...],replace:true}` (max 300; dates `YYYY-MM-DD`; `replace` deletes rows missing from the list). `node scripts/import-outreach.mjs [--dry-run]` parses the tables in `../tracker/outreach.md` (Name, Organization, Sent, Status, optional Last reply and Email/Domain columns; notes and next steps stay local) and posts them with `~/.config/jarvis/admin_key`. Re-run it after editing the tracker. The scheduler sends `📨 Follow up with NAME at ORG — sent N days ago` once at 7 days and once at 14 (each in a 7-day window; nothing after 21 days), outside quiet hours, not while paused, only for rows with a sent date, no reply date and a status that isn't replied/closed/declined/met. Gmail triage marks a row replied (`replied_at`, audited `outreach:replied`; imports never clear it) when a DKIM/DMARC-verified In-Reply-To reply comes from the row's domain or with the contact's exact name as sender (free-mail domains match by name only).
- **Job scout** (`src/scout.js`, `scout_jobs` table): Mondays and Thursdays from 6:00 Chicago, one public board per 5-minute tick (`BOARDS` in `src/scout.js`: Anduril, Palantir, Shield AI, Saronic, Scale AI, Point72, Accenture Federal, HawkEye 360, Rocket Lab, SpaceX, Varda, K2 Space, Divergent, Battery Ventures, Hermeus, Northwood; each slug checked live 2026-10-05). Code filters to internship/new-grad titles in defense, finance, policy, ops (engineering and senior titles dropped) in the US or remote. No model reads board text; titles are scrubbed and injection-like titles dropped; links are built from the slug and a pattern-checked posting id. Once every board is scanned and quiet hours end, Telegram gets the top 5 new roles (title, company, location, link; same title in several cities counted once), once per scan day, plain text with previews off. A failing board sets source `scout` to error with its slug. Paused → no scan, no send.
- **Sunday review** (`src/review.js`): in the weekly window, one Telegram message built by code: audit action counts for 7 days (names only, no targets), food averages vs `/target`, count of emails that needed attention and phishing flagged, outreach due, new scout finds, and open deadlines in the next 14 days. Once per Sunday, not while paused.

To rotate the token: `/revoke` in BotFather, then `wrangler secret put TELEGRAM_BOT_TOKEN` and re-run setWebhook.

## Safety tests and AI budget

`tests/fixtures/hostile.json` holds about 30 hostile inputs (phishing, prompt injection, hostile calendar titles, task notes, headlines, GroupMe-style messages). `npm test` runs each through triage, alerts, news, chat and Telegram and checks that nothing creates a proposal and no link, address or phone number from untrusted content or model output gets through. Add a case whenever a prompt or model changes.

Every Claude call goes through `src/budget.js`, which records calls and tokens per Chicago day in `llm_usage` (migration 0009). The cap is `preferences.llmDailyTokenCap` (default 400000; set it with `POST /api/preferences {"llmDailyTokenCap":N}`, 10k to 5M). Over the cap, email is left unsorted in the digest, news is plain headlines, chat replies that the limit is reached, and Telegram gets one notice that day. The cost estimate uses Haiku 4.5 list prices (`PRICES` in `budget.js`).

## Google setup

Use a Google Cloud project you control. Enable Calendar API and Gmail API, configure Google Auth consent for personal use, and create an OAuth **Web application** client with this exact authorized redirect:

`https://your-worker.example.workers.dev/oauth/google/callback`

Download the client JSON to a private location outside this repo. Run:

```sh
node scripts/configure-google.mjs /absolute/path/to/client.json
```

Then open Beacon → Connections → Connect Google. Authorization uses calendar.readonly and gmail.readonly; it cannot modify Calendar or send email. Refresh tokens are encrypted in D1 using a key derived from the Worker secret. Rotating `GATEWAY_KEY` requires reconnecting Google. Initial Gmail sync establishes a baseline without alerting on old mail. Later checks prioritize application/interview/deadline updates and replies; digest-level mail is listed (with sender domain) in the morning brief. School record mail (uchicago.edu with grade/roster/transcript/registrar wording) only gets a generic "open it directly" alert: no model call and no stored subject. Calendar invites Jackson hasn't accepted (needsAction/declined, or organized by someone else and not accepted) are skipped.

A Google consent app in Testing can issue refresh tokens that expire after seven days. Choose the appropriate production/personal-use configuration or expect reconnection. Sources: [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [token expiration rules](https://developers.google.com/identity/protocols/oauth2).

## Voice activation

Before enabling voice, provision/verify an owned voice-capable number in the correct Twilio account, complete ConversationRelay onboarding, and set its incoming-call webhook to POST:

`https://your-worker.example.workers.dev/voice/incoming`

Phone numbers are Worker secrets `TWILIO_NUMBER` and `OWNER_NUMBER` (not vars). Run `node scripts/beacon.mjs voice-pin`, and set `VOICE_ENABLED` true only after checking account readiness. Deploy and test a real call. The inbound route checks Twilio signatures and the caller number; a short-lived one-use token authorizes its WebSocket. Conversations cap at ten minutes/40 turns and require verbal confirmation before saving. Outbound `/call` remains the legacy read-aloud route, not a two-way outbound conversation. Automatic call escalation is not enabled.

## Operations

```sh
npm ci
npm run check
npx wrangler d1 migrations apply jarvis-assistant --remote   # includes 0008_mail_feedback (mail votes, sender_rules), 0009_llm_usage (daily AI budget), 0010_session_hardening (session last_seen/device, rate_limits), 0011_contacts (contacts, bridge_calls), 0012_finance (charges, known_subscriptions), 0013_career (outreach, scout_jobs)
npm run deploy
node scripts/beacon.mjs status
```

`npm run check` runs SQLite-backed behavioral/security tests, builds the UI, and checks the Worker bundle. Browser visual testing requires an attached browser; none was available during setup. Phone audio and actual device push must be verified after activating those endpoints.

Private credentials stay in `~/.config/jarvis/` and Worker secrets. Required: `GATEWAY_KEY`; push: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`; optional Google/Claude/Twilio credentials. Never place secrets in `wrangler.jsonc`, frontend code, logs or git. D1 contains personal tasks, check-ins and conversation history.

Rate limits (D1 `rate_limits`, fixed windows keyed by a hash of `CF-Connecting-IP`; no extra binding): `/api/login` 10 per 15 min, `/voice/incoming` 10 per hour, `/oauth/google/callback` 10 per hour, failed `X-Jarvis-Key`/`X-Jarvis-Admin-Key` 20 per hour (after that even the right key gets 429 until the window ends). Over the limit returns 429 and writes one `ratelimit:blocked:<scope>` audit row per window. The scheduler deletes expired counters and idle/expired sessions.

Keys: `X-Jarvis-Key` (service, `~/.config/jarvis/gateway_key`) reaches only import, source, tick, `/call` and GroupMe routes. It cannot read user data, chat, confirm or mint logins. `X-Jarvis-Admin-Key` (`~/.config/jarvis/admin_key`, laptop only) mints access links and reads status. Confirmations execute only a stored proposal ID (one-use, 10-minute expiry, argument hash checked). Google tokens are encrypted with the separate `TOKEN_ENC_KEY`.

## Agent (M7, migrations 0029–0031; design in [decisions/agentic-beacon.md](../decisions/agentic-beacon.md))

With the `AGENT_MODE=true` var set (leave it unset until a deploy's tests are green; off, `converse()` is byte-for-byte the old single-shot path), natural asks from Telegram, the web app and voice go to a planner loop in `src/agent.js`: Sonnet (`claude-sonnet-5-5`) plans with small read-only **lookup tools** and ends in at most **one action**; code owns every side effect through the registry in `src/actions.js`. Deadlines per channel: Telegram 18 s (in `waitUntil`, with "typing…" before each planner call), web 25 s, voice 10 s ("Let me check." before the first lookup). Caps per turn: 8 tool calls (voice 3), 3 `email_search`, 3 `email_read`, 40k weighted input tokens; per day 60 planner turns (20/hour) and `preferences.agentDailyTokenCap` (default 1M weighted), separate from the triage budget. Over any cap, or on a failure before the first model response, the single-shot path answers; after a tool ran it never does (no double effects), and a code-built partial reply is logged as an error row.

- **Lookups**: `calendar_search` (classes / work / personal filters; synced `events` table inside −1d..+15d, live read-only Google outside it with `live:` ids), `calendar_free`, `tasks_search`, `contacts_search`, `notes_search` (knowledge base), `groupme_recent` (Club, code-built lines), `email_search` (metadata only, either account, sender candidates minted by code), `email_read` (a tool-less Haiku `claude-haiku-4-5-20251001` summary of ≤120 words, scrubbed and injection-filtered; the body never reaches the planner or D1), plus `mail_status`, `day_brief`, `meals_today`, `weather` as code text. Every string a tool returns is clipped, scrubbed of links, addresses and numbers, injection-filtered and wrapped in `<untrusted_data>`; email, notes and GroupMe results **taint** the turn: Auto actions become approval cards (`task_add` → capture, `task_done` → check-in), drafts to saved contacts become a Confirm card with the full text, contacts and Mac tasks are refused.
- **Actions**: `propose` (any registry type), `draft_email` (to/cc/bcc are contact ids or a verified sender's email id, never an address; a new sender becomes one `contact_and_draft` Confirm card that saves the contact and writes the draft; `reply_to_id` makes an in-thread reply with To, Re: subject, In-Reply-To and References set by code), `request_capability` (logged to `capability_requests`; on an untainted turn also proposed as a Mac build job in Jackson's own words), `clarify` (one question, no side effect).
- **Fast paths stay** (schedule, assignments, mail, "what's next", "list my tasks", undo, server triggers) behind a gate in `src/schedule.js` (`fastPathGate`): ≤10 words, one domain, no "and/then/also", no named person, course, numbered item or cross-reference ("free", "before", "Club", "weather"). "am I free before my econ pset is due?" and "what's due tomorrow and is anything in my email about it" therefore reach the planner.
- **Working set** (`settings.agent_working_set`, 30 minutes): email aliases (ids, names, addresses only), event and task ids, last tools and list. The follow-up resolver ("the first one", "and Friday?") is not built yet.
- **Interaction log**: one `interactions` row per turn from every channel (his words, tool names/timing/arg keys, reply unless it held an email summary, action and outcome ids, latency, tokens, short error codes, taint). Corrections are detected by code from the next message or a button tap. `/log` and `/log trouble` in Telegram, the Log tab in the web app (`GET /api/interactions`, one-tap wrong/fine labels), and `reviews/interactions-YYYY-MM-DD.md` on Sundays (counts, his asks, tool names, outcomes, corrections, clusters, gaps, eval runs, proposed fixes; replies never leave D1). Rows purge after 90 days.
- **Eval set**: `tests/fixtures/asks.json` (261 predicted asks, stable ids `a001`–`a261`); 60 carry `route`, `eval_phrases` and `expect {tools, action, must_not}`. `npm test` runs that routing table with a scripted planner: fast paths answer with no model call, agent asks run their lookups and end in exactly the expected action, read phrasing never changes anything, and the four hijack cases go to the agent. Three entries name tools or actions not built yet (`scout_recent`, `tracker_status`, spending) and must end in `request_capability`: the fixture doubles as the backlog.
- **Replay on the Mac**: `node scripts/agent-eval.mjs` runs a fixed 40-phrase sample (`--all` for every phrase, `--only=a006,a088`, `--dry-run`, `--no-post`) through the real planner on an in-memory SQLite copy of the schema with fictional seeded rows and mocked email/GroupMe/weather tools, so nothing touches Google, Telegram or the live database. Key from `ANTHROPIC_API_KEY` or `~/.config/jarvis/anthropic_key` (without it, agent asks are skipped, not failed); cost is about $1–3 per 40-ask run. The report (asks, tool names, action types, reply snippets) is written to `research/agent-eval/DATE.md` (git-ignored); only counts, failing ask ids and code-built notes are posted to `POST /api/eval/result` (admin key) as an `eval_runs` row plus one `capability_requests` row per failing ask per day, which the Sunday interaction review lists under Gaps and Eval runs. Run it weekly from launchd or by hand after prompt or tool changes.

## Notes and feedback → GitHub

With the `GITHUB_TOKEN` Worker secret set (fine-grained: this repo only, Contents + Issues read/write, 90-day expiry), each note is committed to `notes/INBOX.md` and each piece of feedback becomes an issue labeled `feedback` (with call context). Only those two calls are allowlisted in `src/github.js`. Anything that fails is retried by the scheduler; `scripts/export-notes.mjs` is the manual fallback. On the laptop: `gh issue list --label feedback`.
